# AKDAgent 变更记录 · 音频分析升级

> 本文件记录 AKDAgent 音频分析功能的迁移与新增。创建于 2026-08-28。
> 目的：让后续排查/继续时快速对齐「已完成」「待改」与「关键决策」。

## 一、本次改动（音频分析迁移 + 情感/和弦新增）

### 目标
用户要求：音频分析（干声提取 / BPM / 调性 / 和弦）**用 ONNX 预训练模型替代 essentia**，并新增**音频情感分析**。

### 关键调研结论（重要，避免重复踩坑）
1. **BPM / 调性 / 和弦没有可用的现成 ONNX 模型**：
   - 贴音乐的 AST 模型（如 `LaurenGurgiolo/Music_by_Emotion`）只有 PyTorch（.pth/.safetensors，344MB），需自转 ONNX，且要完整 mel 谱前置，工程量大。
   - 现成 ONNX 情感/和弦模型**全是语音情绪识别**（wav2vec2，378MB~1.26GB），不贴歌曲。
   - 唯一沾边音乐的 `livechord-*` 是 Python 前置 beat_tracker + CQT 特征链路，不适合 Node。
   - **结论**：走「纯 JS DSP 方案」，而非强行迁 ONNX。
2. **CREPE（干声→音符）例外**：有干净的 ONNX 导出（`wok000/weights`），已成功迁移并提速。

### 用户最终决策（走法②）
- 音频情感用「四象限 Valence-Arousal 映射」（基于已有物理特征），非预训练模型。
- 音频分析走「纯 JS DSP 自实现」，并**保留 MIDI 链路**（`sv_extract_notes` CREPE→音符）。

## 三、实测数据

### DSP 合成信号验证（全部通过）
- chroma：C 大三和弦 → 峰位精确 C/E/G，其余 0.000
- 调性 Krumhansl：C 大调→C major(0.95)，A 小调→A minor(0.88)
- 和弦：Am→Aminor=1.0，G→G=1.0
- 能量/音区：rms 大>小，pitchMedian~440，centroid 440

- `sv_analyze_audio`：key=E major、bpm=88、rms=0.022、centroid=3387、pitch=419.9、59拍

## 四、待改 / 待办（后续）

### ① `@audio/beat` 准确性与参数（已处理 BPM 歧义）
- `sv_align_audio` / `sv_apply_tempo` 依赖 `firstBeatSec`/`beatTicks`，现由 `@audio/beat detect` 提供。
- **已知问题（2026-09 实测真实歌曲《怖画》发现）**：`@audio/beat` 的 BPM 检测**有歧义**——同一段音频在自由/限定区间（60-90/110-130/140-160）都能报 conf=1 的不同 BPM（如 150 / 121 / 75），且 `confidence` **无区分度**（都=1）。实测歌曲自由检测 150，但 110-130 区间检出 121（≈120），说明 **120 可能是真实 BPM，150 是翻倍/半拍混淆**。
- **解决（2026-09 已实现）**：
  - `sv_analyze_audio` 返回 **`bpmCandidates`**（如 `[{bpm:120},{bpm:112},{bpm:150},{bpm:87}]` 各自 confidence），揭示歧义供用户判断。
  - `sv_analyze_audio` / `sv_align_audio` / `sv_apply_tempo` 支持 **`bpm` 参数**：传入后用 `@audio/beat beatTrack({ bpm })` 按指定 BPM 重算拍点，避免被误检 BPM 带偏。
  - 用法：先 `sv_analyze_audio` 看 `bpmCandidates` → 判断真实 BPM → 传给 `sv_align_audio`/`sv_apply_tempo` 的 `bpm`。

### ② `@chordkit/detect`（调研但未用）
- 调研过 `@chordkit/detect`（从 MIDI 音符/频率检测和弦，质量高），**最终用自写 chroma（`dsp.detectChord`）实现 `sv_analyze_chord`（纯音频）**。
- 若想提高和弦质量，可后续加一条「干声→CREPE音符→`@chordkit/detect`→和弦」的 MIDI 侧工具（用户要求保留 MIDI 链路，目前 `sv_extract_notes` 承担音符侧）。

### ③ 体积 / 打包
- MCP server（含模型/依赖）**不进 Electron 安装包**——`cordis.patch.yml` 用系统 node 直接跑 `server/dist/index.js`。NSIS/MSI（~282MB）不受此次改动影响。
- 若要在安装包内置 server+模型（开箱即用），需把 `server/dist`+`server/models`+`server/node_modules` 加进 `electron-builder.yml` 的 `extraResources`，体积 +约 400MB。

### ④ 文档同步
- 「提问应答失败排查.md」等文档需同步新工具名。
- 可补充 `sv_analyze_chord`/`sv_analyze_emotion` 的调用示例。

### ⑤ 复核
- MCP server 由 DSH host 自动拉起（启动命令 `server/dist/index.js`）。改动后需确认其加载了新工具（`tools/list` 应为 **30** 个）。若崩溃或重启，DSH 会自动拉起。
  > 🧹 2026-09-17 更正：原文写「22 个」是**最初版本**的数字；现役工具数为 **30**（清单见 `knowledge/docs/MCP工具清单.md`，`tools/check-tool-inventory.cjs` 做零漂移校验）。

# 歌词时序对齐 + 指定正式轨填词（sv_fill_lyrics_to_track）

> 独立主题，记录于 2026-08-30。

## 背景：SV 干声转录
- SV（Synthesizer V）能对导入的干声**转录出音符轨**（如 `轮转的维也纳_main`）：音符带 **pitch + onset + 拼音/音位歌词**（如 "si xu gong qi"，`.tsh uo cl` 为 xsampa 音位）。**无需外部 STT**。
- 转录的拼音有错误（同音字/音位含混），需要**模型理解**修正为正确汉字歌词。

## 工作流（参考转录轨 → 正确歌词 → 填正式轨）
1. 读转录轨音符（拼音 + onset 时间）作为参考。
2. **模型**把拼音序列理解/修正为**正确汉字歌词**（结合参考 `.svp`/语义）。
3. **填到正式轨**：指定"已有空音符"的轨道，按时间顺序/音符顺序把正确歌词逐字填入。

## 新增工具：`sv_fill_lyrics_to_track`（当时第 25 个工具；**现共 30 个**，见 `MCP工具清单.md`）
- **参数**：`lyrics`（正确歌词文本，中文逐字/英文按词，`-` 停顿）、`track`（轨道名称或索引（**索引 0 起**的轨道下标），**可省略=当前轨**）、`host`（sv/ix）。
- **桥侧 op `fill_track_lyrics`**：按名称/索引（**0 起**）定位轨道 → 取第一个非 instrumental 组 → 逐音符 `setLyrics` 填入。
- 支持指定轨道（名称/索引）或不指定（当前轨）。

## 验证（SV1，0 差异）
- 手动流程：`Track 2`（脚本填词，321音符/306字）vs `未命名音轨 2`（已完成标准轨）逐音符对比 = **0 项差异**，完全一致。
- 证明"读转录轨 → 正确歌词 → 指定空音符轨 → 按序填词"流程准确可靠。

## 歌词相关工具（4 个）
`sv_set_selected_lyrics`（统一设词）、`sv_apply_lyrics`（逐字对位，无轨道指定）、`sv_align_lyrics`（LRC 时间戳对齐）、`sv_fill_lyrics_to_track`（**新增，指定轨道**）。

## 注意
- host 运行版本需含 `fill_track_lyrics` op（改桥后需重跑）。
- "拼音→正确汉字"依赖模型理解（模型强项）；工具只是读写载体。

# 附：和弦 / 情感分析调用示例（P11 · 2026-09-17 补）

> 这两件工具最容易被漏掉（文档里长期只有工具名、没有例子）⇒ 在这里补齐；工具清单与参数以 `knowledge/docs/MCP工具清单.md` 为准（`tools/check-tool-inventory.cjs` 做零漂移校验）。

**和弦估计 —— `sv_analyze_chord`**（输入必须是 **WAV**；建议用**纯伴奏**，带人声混音的 chroma 会不准）

```
sv_analyze_chord(input="D:/proj/accompaniment.wav", startSec=0, endSec=30, maxCandidates=3)
→ { best: {root:"C", quality:"maj", score:0.83}, candidates: [...], chroma: [12 个数] }

# 典型用法：先分离出伴奏，再估和弦，最后把骨架铺成音符
sv_separate_vocals(input="D:/proj/song.wav")        # → vocal.wav / accompaniment.wav
sv_analyze_chord(input=".../accompaniment.wav")      # 只对纯伴奏做，别喂混音
sv_write_chords(input=".../accompaniment.wav", pattern="block", segBeats=4, startMeasure=2)
```

**情感分析 —— `sv_analyze_emotion`**（本地零下载；输入同样需 WAV）

```
sv_analyze_emotion(input="D:/proj/verse.wav", startSec=12, endSec=42)
→ { valence: 0.31, arousal: 0.62, quadrant: "愤/悲伤", label: "...", emoji: "…",
    features: { key:"Am", bpm:96, rmsDb:-18.4, pitchMedianHz:220 } }

# 典型用法：整曲按段落各跑一次，比对情绪走向，给编曲/织体选型做依据
sv_analyze_emotion(input=".../song.wav", startSec=0,   endSec=32)   # 主歌
sv_analyze_emotion(input=".../song.wav", startSec=32,  endSec=64)   # 副歌
```

**共同注意点**：① 只吃 **WAV**（非 WAV 先 `sv_convert_audio`）；② 分段分析（`startSec`/`endSec`）比整曲更有意义；③ 结果是**参考级**，不是转录级 —— 别当成"标准答案"往工程里硬写。
